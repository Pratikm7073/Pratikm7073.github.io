# Retail Resource Planning & Forecast Engine

A working demand-forecasting and capacity-planning engine for a multi-channel contact
centre — built around the way a water retailer's Retail operation actually behaves:
billing-led demand, a 24/7 operational emergency line, weather-driven spikes, and a small
Welsh-language skill pool that cannot be pooled with anything else.

**[▶ Live interactive demo](https://pratikm7073.github.io/planning-engine.html)** — move the
sliders and the whole Erlang calculation re-runs in the browser.

> **All data in this repository is synthetic.** It is generated by
> [`synth.py`](src/dcww_planning/synth.py) from a seeded random process. No real operational
> data is used anywhere. The *structure* is faithful to how a UK water retailer's contact
> operation works; the *numbers* are invented. The engine reads a documented CSV schema, so
> a real extract drops straight in — see [Data schema](#data-schema).

---

## What problem this solves

A resource plan has to answer four questions at once, and getting any one of them wrong
makes the other three worthless:

1. **How many contacts are coming?** By queue, by channel, by day — and by half hour,
   because a daily total is not a plan.
2. **How many advisors does that need?** Queueing theory for anything the customer waits
   on, workload arithmetic for anything that can be banked against an SLA.
3. **How many advisors will actually be there?** Attrition erodes headcount every week and
   recruits are not capacity for fourteen weeks.
4. **What do we do about the gap?** Priced, with the levers that are still available given
   how far out it is.

This engine does all four, end to end, and reports its own accuracy.

## Results

Measured by **rolling-origin backtest**: the model is re-fitted at successive cut-off dates
and scored only against data it could not see, pooled across every origin.

| | Result |
|---|---|
| Service lines forecast | **16** across 5 channels |
| Seasonal-naive baseline | **26.2%** WAPE |
| Engine (selected model per line) | **16.3%** WAPE |
| **Mean error reduction** | **35.8%** |
| Lines beating the baseline | **16 / 16** |
| Unit tests | **130** |

Four findings the engine produces that are worth more than the accuracy number:

**Shrinkage compounds — it does not add.** The components sum to 31.4%, but they compound
to **27.8%**. And the requirement is grossed up by *dividing* by (1 − shrinkage), never by
multiplying by (1 + shrinkage): per 100 advisors needed on the phone that is **138.4 FTE
rostered, not 127.8** — a 10.6 FTE error, always in the direction of under-staffing, and
completely invisible in a spreadsheet because both numbers look plausible.

**Erlang C over-staffs, and it can be quantified.** Erlang C assumes infinitely patient
customers who never hang up, so it sizes for a queue that in reality partly clears itself.
An exact Erlang A birth–death model over the same volume range needs **718 advisors where
Erlang C asks for 858** — Erlang C wants **19.5% more** to hold a 5% abandonment target.

**Volume does not scale headcount linearly.** A 10% volume increase needs **8.7%** more
FTE, because larger queues pool their variance better. Scaling a plan by the volume
multiplier — the intuitive shortcut — buys people who are not needed. Every scenario in
this engine re-runs the full half-hourly sizing rather than scaling the answer.

**The efficient roster is not the hireable one.** Left to optimise freely, shift covering
fills a double-humped curve almost entirely with four-hour shifts: 83.2% roster efficiency,
and a roster nobody can recruit for. Capping part-time at a realistic 35% of hours costs
1.7 points (81.5%); full-time only costs 9.3 points (73.9%). The trade-off is a parameter,
not a constant, so it can be argued about with the resourcing team.

## How it maps to the role

Built against a Planning Specialist job description for a Retail Planning & Performance
team. Each requirement maps to something you can run:

| Job description requirement | Where it lives |
|---|---|
| Forecasts and resource plans — short, medium and long term | [`planner.py`](src/dcww_planning/planner.py), horizons at 28 days / 26 weeks / 24 months |
| Develop and use bespoke planning and forecasting models | [`models.py`](src/dcww_planning/models.py) — three competing models, selected by backtest |
| Achieve KPIs in the most cost-effective manner | Occupancy caps, cost model, scenario pricing, [`risk.py`](src/dcww_planning/risk.py) mitigations |
| Operate WFM/WFO systems for forecasting **and scheduling** | [`capacity.py`](src/dcww_planning/capacity.py) — interval requirements → shift patterns → roster |
| Investigate contact centre metrics and trends | [`backtest.py`](src/dcww_planning/backtest.py) — WAPE, MAPE, bias, tracking signal by horizon |
| Pan-Retail, multi-channel plan | 5 channels × 8 queues = 16 service lines, planned together |
| Real Time Analysis, adherence, off-line exceptions | [`rta.py`](src/dcww_planning/rta.py) — intraday re-forecast, adherence vs conformance, action list |
| Identify future issues and propose mitigation | [`risk.py`](src/dcww_planning/risk.py) — early-warning register with recoverability test |
| Good knowledge of Excel is essential | [`excelpack.py`](src/dcww_planning/excelpack.py) — 9-sheet pack with **live formulas** |

## Quick start

```bash
pip install -e ".[dev]"

python -m dcww_planning generate    # write the synthetic dataset
python -m dcww_planning backtest    # rolling-origin accuracy + model selection  (~30s)
python -m dcww_planning plan        # build the plan, export the Excel pack       (~20s)
python -m dcww_planning rta         # in-day analysis for one day
python -m dcww_planning web         # JSON payload for the browser demo
python -m dcww_planning all         # everything, in order

pytest                              # 130 tests, ~30s
```

Outputs land in `out/`: `retail_planning_pack.xlsx`, `weekly_plan.csv`,
`daily_forecast.csv`, `interval_requirement.csv`, `risk_register.csv`, `scenarios.csv`,
`backtest_summary.csv`, `rta_position.csv`, `rta_actions.csv`.

Backtesting is the slow step, so model selection is cached to `out/model_selection.json`
and reused. Pass `--refresh` to re-run it.

## How it works

```
calendarwales.py   Bank holidays (computed, incl. substitute days) + the Retail
                   charging calendar: charges notification, tariff change, bill
                   despatch waves, direct debit dates, meter reads, HelpU and
                   PSR campaigns, freeze–thaw, storms, dry spells.
        ↓
synth.py           Seeded synthetic history. Shares no seasonal code with the
                   estimator, so the backtest is not circular.
        ↓
features.py        Design matrix: trend, day-of-week dummies, annual Fourier
                   terms, bank-holiday adjacency, event regressors. Plus the
                   structural-break test and the outlier rule.
        ↓
models.py          Seasonal naive · multiplicative decomposition · ridge on log
                   volume. Fitted in two passes.
        ↓
backtest.py        Rolling origin. WAPE / MAPE / bias / bias ratio by horizon.
                   Picks a model per line at the short-term horizon.
        ↓
erlang.py          Erlang B/C (exact), Erlang A (exact, birth–death),
                   deferrable workload model.
        ↓
capacity.py        Interval sizing → shrinkage → shift covering → roster.
                   Supply: attrition, training, nesting, recruitment pipeline.
        ↓
planner.py         Joins it all: forecast → requirement → supply → gap → cost.
                   Scenarios re-run the whole thing.
        ↓
risk.py            Early-warning register with recoverability and mitigations.
rta.py             In-day re-forecast, adherence, off-line exceptions.
excelpack.py       The planning pack.  webexport.py  The browser demo payload.
```

### The service lines

Sixteen planning entities, because this is the level a plan is actually built at. Rolling
up to "total contacts" hides that a 24/7 emergency queue and a weekday billing queue need
completely different shift patterns; rolling down to individual skills produces volumes too
small to forecast.

| Queue | Channels | Hours | Notes |
|---|---|---|---|
| Billing & payments | Voice, chat, email, social, back office | Mon–Sat | The volume engine; drives the February charges peak |
| Metering | Voice, email | Mon–Sat | Quarterly read cycle |
| Leaks & supply interruption | Voice, social | **24/7** | Freeze–thaw driven; cannot close |
| Water quality | Voice | **24/7** | Longer handle time |
| Affordability & debt | Voice, back office | Mon–Sat | HelpU / WaterSure; +34% AHT |
| Move home | Voice, chat | Mon–Sat | Summer-peaking |
| Welsh language (Cymraeg) | Voice | Mon–Sat | ~58/day — planned separately on purpose |
| Complaints | Back office | Mon–Fri | +55% AHT |

## Design decisions worth defending

These are the places where the obvious approach is wrong, and wrong quietly.

### Structural breaks are found by refitting, not by scanning residuals

The generator plants a self-serve portal launch that permanently deflects billing voice
into web chat. The obvious detector — fit a model, scan its residuals for a step — **fails
completely**, and it fails confidently:

- A level shift that ramps in over eight weeks, seen through two years of history, is very
  nearly collinear with a free linear trend. The trend absorbs it, the residuals come out
  flat, and the model attributes a one-off portal launch to organic decline — which then
  gets extrapolated forward forever.
- On the sibling series the same collinearity produces the opposite failure: an over-fitted
  trend leaves a spurious step, and the scan reports a break that never happened.

The fix is to make trend and shift **compete**. For each candidate date, refit the whole
model with a ramp regressor added and score it on BIC; accept only if the improvement is
decisive *and* the step is material. Result: found on **both** planted lines (within 6 and 2
days of truth) and **zero false positives** across the other 14.

### Outliers are flagged on residuals, never on raw volume

Flagging raw volume as anomalous flags every freeze–thaw week on the operational line.
Those are not anomalies — they are the event regressors doing their job, and removing them
deletes the signal the model needs. Run the rule on residuals and it asks the right
question: *what is left that the calendar, seasonality and known events cannot explain?* It
finds the planted trunk-main incident and leaves the freeze–thaw weeks alone.

Flagged days are excluded from refitting but **not deleted**. An incident that generated 7×
normal volume is real demand that really had to be answered; it belongs in the resilience
conversation, just not in the estimate of what a normal Tuesday looks like. And because
incidents are almost all upward spikes, the retransformation factor is computed over *all*
residuals including the excluded ones — robust shape, unbiased level.

### An annual index needs an annual window

The classic decomposition takes the ratio to a centred moving average. For an *annual*
index that window has to be 365 days wide — anything narrower follows the annual cycle
itself, the ratio comes out at ~1.0 everywhere, and the seasonal index collapses to flat.
The symptom is a forecast that never comes down in summer on a winter-peaking queue; on the
24/7 operational lines it was a **47% WAPE** error before it was fixed, and 7.9% after.
Two and a half years cannot support a 365-day centred window at the edges, so the long-run
level is fitted explicitly as a robust line instead.

### Deferrable channels are not queues

An email answered in six hours is as compliant as one answered in six minutes. There is no
waiting-time distribution to satisfy — only enough productive hours to work the stock down
inside the SLA. Running Erlang C on an email queue sizes it for instant answer and can
easily double the requirement.

### The occupancy cap is a real constraint

Erlang C will report that N advisors hit 80/20 at 97% occupancy. That is arithmetically
true and operationally fictional: at 97% occupancy there is no gap between contacts, and
within a fortnight real AHT rises, adherence falls and attrition climbs. Every interval
records which constraint actually bound — service level or occupancy — so a planner can see
at a glance which kind of problem they have.

### Adherence and conformance are different measures

**Conformance** asks whether the hours worked matched the hours scheduled. **Adherence**
asks whether people were on the phone *when the queue needed them*, capping credit at the
scheduled level so being over-staffed at 11:00 cannot offset being short at 15:00. An
operation can run 100% conformance and 75% adherence — everybody worked their hours, just
not at the right times — and that combination is one of the most common causes of a service
level that misses despite the headcount being right.

### The in-day re-forecast is damped, and the damping rises through the day

Intraday variance is largely noise: an hour running 20% hot is usually a busy hour, not the
first hour of a 20% day. An undamped re-forecast chases it, and an RTA desk that reacts to
every wobble spends its overtime budget by ten in the morning. Damping scales with how much
of the day has elapsed — at 09:00 a +7.5% variance produces a +3.2% revision; by 17:00 the
same variance produces +11.1%.

### Recoverability is the test that changes behaviour

A shortfall inside the 14-week recruitment pipeline **cannot be hired for at any price**, so
raising it as "we need to recruit" is useless advice. The risk register separates the two
and gives the unrecoverable ones a different set of levers: leave re-profiling, overtime,
cross-skilling, and proactive deflection.

## Data schema

Replace the generated CSVs in `data/` with real extracts in the same shape and everything
downstream works unchanged.

**`contacts_daily.csv`** — one row per service line per day.

| Column | Type | Meaning |
|---|---|---|
| `date` | date | Contact date |
| `line_key` | str | Service line id, e.g. `billing.voice` |
| `queue`, `channel` | str | Queue name and channel key |
| `welsh_language` | bool | Skill-restricted line |
| `weekday` | int | 0 = Monday |
| `is_bank_holiday` | bool | England & Wales |
| `offered` | float | Contacts offered — **the forecast target** |
| `handled`, `abandoned` | float | Outcome split |
| `aht_seconds` | float | Average handle time, talk + wrap |
| `service_level_attained` | float | 0–1 |
| `workload_hours` | float | `handled × aht / 3600` |

**`interval_profiles.csv`** — `line_key`, `weekday`, `interval` (0–47), `interval_start`,
`share`. Shares sum to 1.0 per line per weekday.

**`contacts_interval.csv`** — half-hourly actuals for RTA: `date`, `interval`,
`interval_start`, `line_key`, `queue`, `channel`, `offered`, `aht_seconds`,
`staffed_actual`, `scheduled`.

Planning assumptions — service levels, AHT, shrinkage components, cost, attrition,
recruitment lead times — all live in [`config.py`](src/dcww_planning/config.py) as named
dataclass fields, so every number a planner would argue about in a review is in one place
rather than buried in the arithmetic.

## Limitations

Stated up front, because the first thing a good interviewer does is look for them.

- **The data is synthetic.** The accuracy figures describe this engine on this generator,
  not a claim about any real operation. The generator shares no seasonal code with the
  estimator so the backtest is not circular — but it is still a simulation, and a real
  operation will contain structure this generator does not.
- **The long-term horizon is not validated.** Backtesting a 24-month forecast needs more
  than 24 months of history to test against. The engine will produce one; the accuracy
  reporting deliberately scores only the in-week, short-term and medium-term buckets rather
  than quoting a number it cannot support.
- **One changepoint, not many.** Two years of daily history cannot support a
  multi-changepoint search without over-fitting.
- **Chat concurrency is an approximation.** An advisor holding 2.2 conversations is
  modelled as 2.2 parallel servers, which is slightly optimistic — real concurrency
  lengthens handle time as it rises.
- **Erlang A is not used for service level.** Its stationary metrics (waiting, abandonment,
  ASA) are exact, but the waiting-time distribution under abandonment is a phase-type
  convolution that is expensive per interval. Staffing runs on Erlang C; Erlang A is there
  to price what that assumption costs.
- **Models under-forecast into sharp peaks.** Visible in the bias column, and it is the
  direction that hurts service — which is why peak weeks carry a risk buffer rather than a
  bare point estimate.
- **Shift covering is greedy, not optimal.** Set covering is NP-hard; the greedy heuristic
  lands within a few per cent on curves this shape and never invents a pattern nobody can
  work.

## Built with

Python 3.10+ · numpy · pandas · openpyxl · pytest. The browser demo is vanilla JavaScript
and hand-written SVG — no charting library, no build step.

Forecasting, queueing and regression are implemented from first principles rather than
pulled from a library, so every number can be traced and defended. Erlang B and C are
verified against published reference tables in the test suite, Erlang A is verified by
converging to Erlang C as patience → ∞, and the ridge solver is verified against ordinary
least squares on a known system.
